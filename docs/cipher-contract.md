# Контракт шифра

## Обязательный интерфейс

Каждая реализация должна соответствовать протоколу `Cipher` из `src/miskzi_ciphers/common/types.py`:

- `name: str`
- `describe() -> CipherInfo`
- `parse_key(raw_key: dict[str, Any]) -> dict[str, Any]`
- `encrypt(plaintext: str, key: dict[str, Any]) -> str`
- `decrypt(ciphertext: str, key: dict[str, Any]) -> str`

Registry дополнительно проверяет, что:

- объект действительно содержит эти члены;
- `name` — непустая строка;
- `name` совпадает с именем подпакета;
- `describe()` возвращает словарь.

## Роль отдельных частей

### `name`

`name` — это системный идентификатор шифра. Он используется:

- в registry;
- в каталоге `data/<cipher_id>/`;
- в UI;
- в тестах;
- в локализации.

`name` не должен быть локализованным заголовком. Это machine-readable идентификатор вроде `caesar`, `cardano_grille`, `ramsey`.

### `describe()`

`describe()` даёт UI и тестам структурированное описание шифра. Фактически важные поля:

- `name` — дублирует системный id;
- `title` — отображаемое название;
- `family` — семейство для UI и документации;
- `params` — схема ввода ключа;
- `notes` — технические примечания.

UI строит форму ключа именно на основе `params`, поэтому `describe()` — это не просто справка, а часть рабочего контракта.

### `parse_key()`

`parse_key()` принимает сырой ключ из UI, JSON или тестов и должен:

- проверить обязательные поля;
- отвергнуть неизвестные ключи, если это поведение выбрано реализацией через `reject_unknown_keys()`;
- привести значения к каноническому виду;
- вернуть словарь, пригодный для `encrypt()/decrypt()`.

Ожидаемый результат — канонический `Key dict`, а не произвольный echo исходных данных.

### `encrypt()` и `decrypt()`

Обе функции работают уже с разобранным ключом. Вызов через `app/service.py` всегда сначала прогоняет сырой ключ через `parse_key()`, но тесты некоторых шифров могут вызывать `encrypt()/decrypt()` и напрямую с заранее распарсенным ключом.

## Требования к `Key dict`

В проекте нет единого класса ключа, поэтому словарь остаётся основным контрактом. Для него важны следующие свойства:

- это обычный `dict[str, Any]`;
- имена полей должны быть стабильны между `describe().params`, `parse_key()` и данными в `variants.json`;
- после `parse_key()` ключ должен быть пригоден как для `encrypt()`, так и для `decrypt()`, если алгоритм допускает обратимость;
- канонизация допускается и ожидается: например, строка может быть приведена к верхнему регистру, число — к `int`, JSON-строка — к списку.

## Валидация и ошибки

Фактическое текущее поведение проекта:

- ошибки в ключе обычно поднимаются как `ValueError`;
- ошибки типа могут быть `ValueError` или `TypeError`;
- сообщения пишутся в самих шифрах и напрямую отображаются в UI;
- общий стиль ошибок — технический и конкретный, например `Missing key 'k'.` или `hill: matrix not invertible mod 33.`

Архитектурный ориентир:

- ошибки должны быть достаточно точными, чтобы понять, какое поле сломано;
- молчаливое исправление невалидного ключа нежелательно;
- лучше канонизировать ожидаемые представления, чем принимать всё подряд.

## Требования к `describe().params`

Каждый элемент `params` — словарь `ParamSpec`. На практике UI использует поля:

- `name`
- `type`
- `required`
- `default`
- `choices`
- `help`
- `example`

### Что считается machine-readable

- `name` — системное имя поля в `raw_key`;
- `type` — технический тип для выбора Streamlit-виджета;
- `required` — влияет на форму и на ожидания тестов;
- `default`, `choices`, `example` — используются при автозаполнении и генерации минимальных тестовых ключей.

### Что считается UI-oriented

- `help`
- `title`
- `notes`

Они тоже важны, но их отсутствие обычно не ломает базовую механику так же сильно, как сломанные `name/type/required`.

## Поведение на невалидных входах

В проекте нет единой нормализации текста для всех шифров. Текущее состояние такое:

- часть шифров работает только с буквами RU_33;
- часть допускает сохранение неизвестных символов;
- часть поднимает ошибку на неподдерживаемом символе;
- `ramsey` принимает только латиницу A-Z и пробел;
- `hill` требует только символы RU_33 и отдельно проверяет кратность длины блока;
- `morse`, `vernam`, `adfgvx` и другие имеют собственные ограничения формата.

Иными словами, поведение с регистром и неизвестными символами определяется конкретной реализацией и должно быть явно зафиксировано в `notes` и тестах шифра.

## Регистр и неизвестные символы

Архитектурный ориентир здесь не в унификации любой ценой, а в предсказуемости:

- если шифр работает только в верхнем регистре, это нужно делать явно и стабильно;
- если шифр сохраняет неизвестные символы как есть, это должно быть совместимо с roundtrip-тестами;
- если шифр отвергает символы вне своего алфавита, ошибка должна быть диагностичной;
- правила должны быть одинаковыми между `encrypt()` и `decrypt()`, если методика не требует иного.

## Что ломать нельзя

- названия полей в `params`, если они уже используются в `variants.json` и тестах;
- смысл `parse_key()` как канонизатора сырого ввода;
- возврат словаря из `describe()`;
- соответствие `cipher.name` имени подпакета.
