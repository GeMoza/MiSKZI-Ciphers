# План реализации practice-layer для ПР9 и ПР10

## 1. Назначение документа

Этот документ планирует реализацию учебного слоя `practice-layer` для ПР9 и ПР10 без изменения основного `CipherProtocol`.

Документ не описывает реализацию в коде и не фиксирует уже существующие модули `practice-layer`.

## Политика интерпретации результатов

- целью реализации является учебно-совместимое поведение алгоритмов, а не побайтное совпадение со сторонними `.exe`;
- корректность результата определяется:
  - правильностью алгоритма;
  - согласованностью выбранных правил: алфавит, нормализация, filler;
  - воспроизводимостью trace;
- допускаются отличия от старых `.exe`, если:
  - они объяснимы;
  - они отражены в документации;
  - они не противоречат базовой логике алгоритма;
- при расхождениях приоритет имеет:
  1. формализованная логика алгоритма;
  2. прозрачность trace;
  3. воспроизводимость результата;
- проект не ставит цель полной обратной совместимости со старыми программами.

## 3. Текущее состояние формализации

| Компонент | Статус | Можно ли реализовывать сейчас | Блокеры |
| --- | --- | --- | --- |
| Caesar ПР9 | рабочее проектное решение принято | да | требуется сверка алфавита методички с runtime-политикой |
| Vigenere ПР9 | рабочее проектное решение принято | да | для `A-Z` может потребоваться отдельный practice-trace или отдельный runtime |
| Gronsfeld ПР9 | рабочее проектное решение принято | да | текущий parser может не поддерживать ключ как список чисел |
| Invert 255 | рабочее проектное решение принято | да | полная совместимость со старым `.exe` не гарантируется |
| перестановка | рабочее проектное решение принято | да | это учебная политика проекта, а не подтверждённая копия `.exe` |
| Playfair | рабочее проектное решение принято частично | да | требуется окончательно зафиксировать русский алфавит и матричную политику |
| Wheatstone | рабочее проектное решение принято | да | полная обратная совместимость со старым `.exe` не гарантируется |
| гистограммы | достаточно формализованы на уровне требований | да | нет точной политики текста для всех режимов |
| trace-модели | достаточно формализованы концептуально | да | требуется выбрать расширяемую модель |
| export | достаточно формализован | да | требуется выбрать итоговый формат полей |
| normalization policies | частично формализованы | да, с параметризацией | единая политика для всех режимов не зафиксирована |

## 4. Общий код, который нужен

Общий код, который можно проектировать и реализовывать независимо от полной формализации всех алгоритмов:
- `PracticeResult`;
- `PracticeStep`;
- `PracticeTable`;
- `HistogramData`;
- `Markdown` / `TXT` export;
- `histogram`;
- базовые функции нормализации;
- частотный анализ;
- адаптер вызова обычных шифров;
- common UI helpers для отображения trace.

Предлагаемые пути:
- `src/miskzi_ciphers/practice/common/models.py`
- `src/miskzi_ciphers/practice/common/export.py`
- `src/miskzi_ciphers/practice/common/histogram.py`
- `src/miskzi_ciphers/practice/common/normalization.py`
- `src/miskzi_ciphers/practice/common/cipher_adapter.py`

Уточнение:
- перечисленные пути являются проектным ориентиром;
- перечисленные пути не означают, что такие модули уже существуют;
- общий код должен быть нейтральным по отношению к конкретному алгоритму и не должен расширять основной `CipherProtocol`.

## 5. Общий код, который может навредить

Не следует объединять в общий код следующие части:
- алгоритмы ПР9 и ПР10 в один общий processor;
- посимвольный trace ПР9 и побиграммный trace ПР10 в одну жесткую модель без расширений;
- гистограммы и матрицы в один общий `analysis object`;
- текстовые политики ПР9 и ПР10 до их отдельной формализации;
- UI-сценарии ПР9 и ПР10 в одну форму.

Дополнительное ограничение:

- политики текста не должны делаться общими без явной настройки режима.

Причины:
- разные типы анализа;
- разные единицы обработки;
- разные отчётные требования;
- риск ложной универсальности.

Архитектурный вывод:
- общий код должен покрывать только инфраструктуру;
- алгоритмический и учебный сценарный код должен оставаться разделённым по практическим работам.

## 6. Разделение по модулям

Предлагаемая структура:

```text
src/miskzi_ciphers/practice/
  common/
  practice_09/
  practice_10/
```

Для `practice_09`:
- `service.py`
- `presets.py`
- `trace_caesar.py`
- `trace_vigenere.py`
- `trace_gronsfeld.py`
- `trace_invert_255.py`
- `trace_pair_swap.py`

Для `practice_10`:
- `service.py`
- `presets.py`
- `bigram.py`
- `matrix.py`
- `trace_playfair.py`
- `trace_wheatstone.py`

Уточнение:
- `bigram.py` и `matrix.py` могут быть общими внутри `practice_10`, но не обязаны быть общими для ПР9;
- если позже появится независимая польза, эти модули можно вынести в `src/miskzi_ciphers/practice/common/`;
- до такой необходимости преждевременный вынос в `common/` не требуется.

## 7. Рекомендуемый порядок реализации

Этап 1:
- `common models`;
- `export`;
- `histogram`;
- `practice adapter`.

Этап 2:
- ПР9: `Caesar` / `Vigenere` / `Gronsfeld` trace для уже существующих шифров;
- presets варианта `5`;
- гистограммы.

Этап 3:
- `Invert 255` на `Windows-1251`;
- простая перестановка соседних символов;
- trace для этих режимов.

Статус:
- MVP-2 реализует `Invert 255` как учебно-совместимый byte-level режим над `Windows-1251`;
- MVP-2 реализует простую перестановку соседних символов как `pair_swap`;
- полная совместимость этих режимов со старым `.exe` не заявляется.

Этап 4:
- реализация `Playfair` как стандартного учебного шифра;
- trace `Playfair`.

Этап 5:
- реализация `Wheatstone` как учебного `two-square`;
- trace `Wheatstone`.

Этап 6:
- UI-вкладки ПР9 и ПР10.

Этап 7:
- тесты и документация.

## 8. Что не делать на первом этапе

Запрещено на первом этапе:
- не менять `CipherProtocol`;
- не переписывать существующие шифры;
- не делать единый универсальный `trace-engine`;
- не пытаться воспроизвести поведение `.exe` по догадкам;
- не смешивать practice presets с обычными `variants.json`, если семантика неясна.

Уточнение:

- `Invert 255` и перестановка допустимы на раннем этапе только как явно зафиксированные учебные политики проекта, а не как заявка на бинарную совместимость со старым `.exe`.

## 9. Блокеры

Ключевые блокеры:
- окончательная спецификация русского `Playfair`;
- полная обратная совместимость `Wheatstone` со старым `.exe`;
- полная обратная совместимость `Invert 255` со старым `.exe`;
- полная обратная совместимость режима перестановки со старым `.exe`;
- единые политики текста без параметризации.

Следствие:
- ПР9 может быть реализована частично раньше ПР10;
- ПР10 может реализовываться по принятой учебной политике, но не должна заявляться как полностью совместимая со старым `.exe`.

## 10. Минимальный MVP

### MVP-1

- practice common models;
- export;
- histogram;
- ПР9 `Caesar` / `Vigenere` / `Gronsfeld`;
- presets варианта `5`.

### MVP-2

- `Invert 255` на `Windows-1251`;
- простая перестановка соседних символов.
- статус: реализован в `practice-layer` как учебно-совместимая политика ПР9 без изменения основного `CipherProtocol`.

### MVP-3

- `Playfair` стандартный учебный.

### MVP-4

- `Wheatstone` учебный `two-square`.

### MVP-5

- UI-вкладки ПР9 и ПР10;
- экспорт отчета.

Итоговая логика MVP:
- первый полезный результат можно получить без ожидания полной формализации всех алгоритмов;
- базовый `practice-layer` целесообразно начинать с инфраструктуры и ПР9;
- для части режимов допускается рабочее проектное решение без гарантии полного совпадения со старым `.exe`;
- ПР10 следует реализовывать как учебный сценарий с явно зафиксированной проектной политикой.
