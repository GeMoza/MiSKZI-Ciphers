# Практическая работа №9 – требования к поддержке в MiSKZI-Ciphers

## 1. Назначение документа

Этот документ фиксирует требования к отдельному учебному режиму выполнения ПР9 внутри проекта `MiSKZI-Ciphers` без запуска внешнего `.exe`.

Документ является проектной спецификацией для дальнейшей реализации и не описывает уже выполненную доработку.

## 2. Источник требований

Подтвержденные факты:
- требования к ПР9 основаны на методическом материале `docs/external-materials/Практическая работа 9.pdf`;
- внешний `.exe` `Лабораторная_работа_1.EXE` не должен запускаться в рамках проекта;
- поддержка ПР9 должна быть реализована средствами собственной программы `MiSKZI-Ciphers`.

Предположения и ограничения:
- материал `docs/external-materials/Практическая работа 9.pdf` находится во внешнем каталоге `docs/external-materials/`, который в проекте считается `non-authoritative`;
- до дополнительной ручной сверки с методичкой точное поведение старой программы должно считаться требующим формализации.

## 3. Суть практической работы

Подтвержденные факты:
- ПР9 посвящена классическим криптоалгоритмам подстановки и перестановки;
- ПР9 требует не только получение результата шифрования/дешифрования, но и анализ преобразований текста;
- отдельной частью работы является анализ гистограмм частот символов.

Предположения:
- учебный режим ПР9 должен совмещать демонстрацию алгоритмов, ручной ввод учебных данных и подготовку материалов для отчета;
- режим ПР9 должен быть ориентирован не на общий список шифров, а на сценарий выполнения практической работы.

## 4. Требуемые функции программы по методичке

Подтвержденные факты:
- текстовый редактор или поле ввода текста;
- открытие `.txt`;
- сохранение `.txt`;
- шифрование;
- дешифрование;
- построение гистограмм;
- сравнение исходного и зашифрованного текстов.

Факты о текущем проекте:
- в Streamlit UI уже есть текстовые поля ввода в `src/miskzi_ciphers/ui/app.py`;
- в CLI уже есть чтение текста из файла через `--text-file` и запись результата через `--out` в `src/miskzi_ciphers/cli.py`;
- в текущем проекте нет готовых гистограмм;
- в текущем UI нет готового импорта файла и экспорта результата через отдельные элементы интерфейса.

## 5. Алгоритмы ПР9

### 5.1 Алгоритмы, уже близкие к существующим

#### Caesar / одноалфавитный метод с задаваемым смещением

- `cipher_id`: `caesar`
- путь реализации: `src/miskzi_ciphers/ciphers/caesar/cipher.py`
- уровень покрытия: поддерживается

Подтвержденные факты:
- в проекте уже есть шифр `caesar`;
- ключ задается параметром `k`;
- шифр работает как общий одноалфавитный сдвиг по русскому алфавиту.

Что требует проверки:
- совпадает ли используемый в ПР9 алфавит со строкой алфавита текущей реализации;
- требуется ли в ПР9 отдельный режим фиксированного смещения, отличный от обычного параметра `k`.

#### Vigenere / многоалфавитный метод

- `cipher_id`: `vigenere`
- путь реализации: `src/miskzi_ciphers/ciphers/vigenere/cipher.py`
- уровень покрытия: частично

Подтвержденные факты:
- в проекте уже есть шифр `vigenere`;
- он использует ключ `keyword`;
- реализация работает по `RU_33`.

Что требует проверки:
- совпадает ли режим ПР9 с текущей реализацией `vigenere`;
- нужна ли латинская версия алгоритма для отдельных учебных примеров;
- совпадает ли логика продвижения ключа по символам с методичкой ПР9.

#### Gronsfeld / ручная задача

- `cipher_id`: `gronsfeld`
- путь реализации: `src/miskzi_ciphers/ciphers/gronsfeld/cipher.py`
- уровень покрытия: требует проверки

Подтвержденные факты:
- в проекте уже есть шифр `gronsfeld`;
- реализация принимает параметр `digits`;
- реализация извлекает из строки только десятичные цифры.

Что требует проверки:
- допускает ли ПР9 ключ вида `7 5 13 19` как последовательность чисел, а не как набор отдельных цифр;
- должна ли логика Гронсфельда в ПР9 работать по русскому алфавиту, совпадающему с текущим `RU_33`;
- совпадает ли интерпретация двузначных значений ключа с текущей реализацией.

### 5.2 Алгоритмы, требующие уточнения или новой реализации

#### Одноалфавитный метод с фиксированным смещением

Что требуется по методичке:
- отдельный учебный режим одноалфавитной подстановки с заранее фиксированным смещением.

Что неизвестно без точного поведения старой программы:
- конкретное значение фиксированного смещения;
- является ли этот режим частным случаем `caesar` или отдельным алгоритмом;
- как именно в старой программе выбирался алфавит.

Что нужно формализовать перед реализацией:
- значение фиксированного смещения;
- используемый алфавит;
- правила обработки пробелов, регистра и символов вне алфавита.

#### Перестановка символов

Что требуется по методичке:
- учебный алгоритм перестановки символов.

Что неизвестно без точного поведения старой программы:
- является ли это блочная перестановка, табличная перестановка или иной режим;
- совпадает ли он с уже существующими `scytale` или `richelieu`;
- какие параметры должен задавать пользователь.

Что нужно формализовать перед реализацией:
- точное правило перестановки;
- размер блока или таблицы;
- формат ключа;
- правила для неполного блока.

#### Инверсия по дополнению до 255

Что требуется по методичке:
- отдельный алгоритм инверсии по дополнению до `255`.

Что неизвестно без точного поведения старой программы:
- выполняется ли преобразование по байтам, по символам или по кодам конкретной кодировки;
- какой диапазон символов допускается;
- как трактуются русские буквы и служебные символы.

Что нужно формализовать перед реализацией:
- кодировка;
- способ преобразования `x -> 255 - x`;
- правила отображения результата обратно в текст.

#### Многоалфавитный метод с фиксированным ключом

Что требуется по методичке:
- отдельный учебный полиалфавитный режим с фиксированным ключом.

Что неизвестно без точного поведения старой программы:
- является ли это частный случай `vigenere`;
- какой ключ считается фиксированным;
- задается ли он пользователем или встроен в алгоритм.

Что нужно формализовать перед реализацией:
- конкретный ключ;
- алфавит;
- правила продвижения ключа;
- поведение на символах вне алфавита.

#### Многоалфавитный метод с ключом фиксированной длины

Что требуется по методичке:
- полиалфавитный режим с ключом ограниченной длины.

Что неизвестно без точного поведения старой программы:
- допустимая длина ключа;
- совпадает ли алгоритм с `vigenere` или `gronsfeld`;
- требуется ли автоматическое повторение ключа.

Что нужно формализовать перед реализацией:
- длина ключа;
- формат ключа;
- алфавит;
- режим повторения ключа.

#### Многоалфавитный метод с ключом произвольной длины

Что требуется по методичке:

- полиалфавитный режим с произвольной длиной ключа.

Что неизвестно без точного поведения старой программы:
- совпадает ли это с текущим `vigenere`;
- допускаются ли только буквы или также цифры;
- как обрабатываются пробелы и знаки препинания.

Что нужно формализовать перед реализацией:
- тип ключа;
- алфавит;
- стратегия продвижения по ключу;
- требования к нормализации текста.

## 6. Вариант 5

Подтвержденные данные варианта 5:
- для Caesar:
  - `N = 5`;
  - `k1 = (N * 2 + 13) mod 17`;
  - `k2 = (N * 4 - 6) mod 13`;
- для Vigenere:
  - ciphertext: `yoikyoj`;
  - key: `work`;
- для Gronsfeld:
  - ciphertext: `сепщвжрм`;
  - key: `7 5 13 19`.

Расчет значений:
- `k1 = (5 * 2 + 13) mod 17 = 23 mod 17 = 6`;
- `k2 = (5 * 4 - 6) mod 13 = 14 mod 13 = 1`.

## 7. Требования к учебному режиму ПР9

Подтвержденные факты:
- режим ПР9 должен позволять выполнить практическую работу без запуска `Лабораторная_работа_1.EXE`;
- режим ПР9 должен быть ориентирован на учебный сценарий, а не только на вызов `encrypt()/decrypt()`.

Минимальные требования к UI:
- выбор алгоритма;
- выбор операции `encrypt` / `decrypt`;
- поле исходного текста;
- поле ключа или смещения;
- выбор варианта;
- preset для варианта `5`;
- поле результата;
- таблица посимвольных преобразований;
- гистограмма исходного текста;
- гистограмма результата;
- экспорт результата в `Markdown` / `TXT`.

Предположения:
- режим ПР9 должен быть отдельным от обычного списка шифров;
- режим ПР9 может использовать существующий `Streamlit` UI как базовую оболочку, но не должен сводиться к простому добавлению новых `cipher_id` в общий список;
- режим ПР9 должен быть отдельным учебным сценарием, который вызывает обычные шифры и дополнительные `practice`-сервисы;
- обычный список шифров не должен получать специфичные элементы ПР9: проверку вариантов, отчетные таблицы, гистограммы и экспорт `trace`.

## 8. Trace / промежуточные расчеты

Подтвержденные факты:
- для учебного выполнения ПР9 требуется промежуточная информация, пригодная для отчета;
- текущий публичный контракт шифров возвращает только строковый результат и не покрывает trace напрямую.

Минимальные данные trace для преобразований:
- исходный символ;
- номер символа в алфавите или кодировке;
- ключ или смещение;
- формула преобразования;
- результат;
- комментарий для отчета.

Минимальные данные trace для гистограмм:
- символ;
- частота в исходном тексте;
- частота в зашифрованном тексте;
- возможное соответствие символов;
- пояснение, как по гистограмме определяется смещение.

Предположения:
- trace должен быть отдельным учебным слоем и не должен изменять основной контракт `encrypt()/decrypt()`;
- trace должен быть пригоден для экспорта в текстовый отчет.

## 8.1 Архитектурная граница учебного режима

Обязательное решение:

- основной `CipherProtocol` и методы `encrypt()/decrypt()` должны остаться строковыми и не должны возвращать учебные объекты;
- гистограммы не являются частью отдельного шифра, а являются аналитическим инструментом практической работы;
- `trace` не должен добавляться внутрь каждого `cipher.py` как обязательная часть контракта;
- учебный режим ПР9 должен быть реализован отдельным слоем поверх существующих шифров;
- существующие шифры могут использоваться как вычислительное ядро, но учебная логика должна жить отдельно;
- новые алгоритмы, если они являются самостоятельными шифрами, могут быть добавлены в `src/miskzi_ciphers/ciphers/`, но их учебный `trace` должен находиться вне основного контракта.

Предлагаемая структура:

- `src/miskzi_ciphers/practice/practice_09/`
- `src/miskzi_ciphers/practice/common/trace.py`
- `src/miskzi_ciphers/practice/common/histogram.py`
- `src/miskzi_ciphers/practice/common/export.py`

Пояснение к предлагаемой структуре:

- перечисленные пути являются ориентиром для изоляции учебного режима;
- перечисленные пути не фиксируют уже существующую структуру проекта;
- конкретная реализация может отличаться по именованию модулей, но должна сохранять выделенный `practice`-layer.

### Взаимодействие practice-layer и core

- `practice-layer` не должен напрямую внедряться в `cipher.py`;
- вызовы шифров должны происходить через отдельный сервис или адаптер внутри `practice-layer`;
- `practice-layer` должен:
  - принимать пользовательский ввод;
  - нормализовать текст;
  - формировать учебный сценарий;
  - вызывать `cipher.encrypt()/decrypt()` как “черный ящик”;
  - дополнять результат `trace`-данными;
- `cipher` не должен знать о существовании `practice-layer`;
- UI режима ПР9 должен работать через `practice`-сервис, а не напрямую через общий `service.py`;
- запрещено вызывать `cipher` напрямую из UI режима ПР9 без промежуточного `practice`-слоя;
- запрещено добавлять условную логику ПР9 внутрь `cipher.py`.

## 9. Нерешенные вопросы

Открытые вопросы, требующие формализации до реализации:
- точное фиксированное смещение в старой программе;
- точное правило перестановки символов;
- точная интерпретация “по дополнению до 255” с учетом кодировки;
- кодировка для `.txt`: `UTF-8` или `Windows-1251`;
- нужно ли воспроизводить исключение символов с кодами `176–223` и `240–255`;
- совпадают ли многоалфавитные методы ПР9 с текущими `vigenere` / `gronsfeld`;
- какие параметры должны быть у фиксированного и произвольного ключа.

Дополнительные открытые вопросы:
- должен ли режим ПР9 работать только с кириллицей или также с латиницей;
- как именно должна строиться гистограмма: по абсолютным частотам, относительным частотам или обеими способами;
- должен ли экспорт включать только итоговые значения или весь trace.

## 10. Предлагаемый план реализации

1. формализовать точные правила алгоритмов ПР9;

6. подключить их к UI-вкладке ПР9 без изменения `CipherProtocol`;
7. добавить недостающие алгоритмы или режимы;

9. добавить тесты;
10. добавить экспорт `Markdown` / `TXT`.

## 11. Ограничения

Подтвержденные ограничения:
- проект не должен запускать внешние `.exe`;
- реализация не должна ломать общий контракт шифров;
- учебный trace не должен подменять основной `encrypt()/decrypt()` контракт;
- режим ПР9 должен быть отдельным от обычного списка шифров.

Дополнительные обязательные ограничения:

- запрещено расширять базовый контракт шифров ради требований ПР9;
- запрещено делать `trace` обязательным методом каждого шифра;
- запрещено смешивать учебные пресеты ПР9 с обычными `variants.json`, если это приведет к неясной семантике обычных вариантов;
- все экспериментальные элементы ПР9 должны быть изолированы в `practice`-слое.

Архитектурные следствия:
- основные шифры проекта должны сохранять совместимость с `src/miskzi_ciphers/common/types.py`;
- учебный режим ПР9 должен строиться поверх существующей архитектуры, а не вместо нее;
- все допущения по методичке ПР9 должны быть явно зафиксированы в документации и тестах до реализации;
- базовый список шифров и учебный сценарий ПР9 должны иметь раздельную ответственность;
- `practice`-layer должен содержать учебные сценарии, аналитику, экспорт и вспомогательные модели, не изменяя семантику обычных шифров.
