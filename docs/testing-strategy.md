# Стратегия тестирования

## Что уже проверяется

Тестовый набор в `tests/` покрывает несколько уровней.

### Контракт и registry

- `test_ciphers_contract.py`
- `test_contract_registry.py`

Эти тесты проверяют, что шифры находятся через registry, умеют возвращать `describe()`, принимают минимально разумный ключ и не ломают базовый roundtrip на безопасных примерах.

### Сервисный слой и пути

- `test_service.py`
- `test_paths.py`

Они страхуют:

- поиск `data/`;
- нормализацию и валидацию `variants.json`;
- миграцию legacy `free_text.txt`;
- чтение и запись `meta.free_text`.

### Схема данных

- `test_variants_schema.py`
- `test_variants_meta.py`

Эти тесты проверяют формат всех реальных `data/*/variants.json` и отдельно поведение `validate_variants_obj()`.

### UI и локализация

- `test_ui_i18n.py`
- `test_ui_localization_labels.py`

Они проверяют наличие основных русских UI-меток и соответствие технических имён параметров локализованным подписям.

### Контрольные векторы

- `test_caesar.py`
- `test_pz3_vectors.py`
- `test_pz4_vectors.py`
- `test_pz5_ramsey_vectors.py`

Здесь лежат более предметные проверки на отдельных шифрах и практиках.

## Какие тесты проверяют контракт

Главные контрактные тесты:

- загрузка шифров через `REGISTRY`;
- корректный `describe()`;
- `parse_key()` на минимальном наборе параметров;
- `encrypt()/decrypt()` возвращают строки;
- roundtrip на безопасных случаях.

Это не доказывает математическую корректность всех алгоритмов, но хорошо ловит инфраструктурные поломки.

## Какие данные считаются проверочными

Проверочными считаются:

- данные из `variants.json`, если они проходят схему и используются в векторных тестах;
- явно зафиксированные примеры в тестах;
- `meta.raw_key_example`, если он реально соответствует контракту шифра;
- `meta.free_text`, если он используется для ручной проверки в Playground.

## Когда нужен новый тест

Новый тест нужен обязательно, если вы:

- добавили новый шифр;
- изменили формат ключа существующего шифра;
- добавили новое семейство данных в `variants.json`;
- изменили правила валидации;
- добавили локализацию новых параметров или нового шифра;
- добавили важный контрольный вектор из методички.

## Когда хватает ручной проверки через UI

Ручной проверки обычно достаточно только для вещей, которые трудно стабильно формализовать и которые не меняют контракт:

- как выглядит форма параметров;
- удобно ли загружается `free_text`;
- понятны ли сообщения Data Manager;
- корректно ли синхронизируются Form и Raw JSON после действий пользователя.

Если меняется поведение данных, контракта или шифра, только ручной проверки недостаточно.

## Как проверять варианты и `meta`

Практический минимум:

1. прогнать `pytest -q`;
2. убедиться, что `service.validate_variants_obj()` возвращает пустой список для нового файла;
3. проверить, что `key` каждого варианта принимается `parse_key()`;
4. если указан `expected`, проверить совпадение результата;
5. открыть шифр в Data Manager и Playground и убедиться, что `meta.free_text` и `meta.raw_key_example` подгружаются без ошибок.
