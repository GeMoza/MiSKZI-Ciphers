# Формат данных

## Базовая структура

Для каждого шифра ожидается файл:

`data/<cipher_id>/variants.json`

Корневой объект всегда должен иметь вид:

```json
{
  "meta": {
    "free_text": "...",
    "notes": "...",
    "raw_key_example": {}
  },
  "items": [
    {
      "id": 1,
      "mode": "encrypt",
      "text": "...",
      "key": {},
      "expected": "..."
    }
  ]
}
```

`service._normalize_variants_root()` нормализует любой прочитанный корень к форме `{"meta": {}, "items": []}`.

## Роль `meta`

Поле `meta` необязательное, но в актуальных файлах оно используется как стандартное место для сопроводительных данных шифра.

### `meta.free_text`

Свободный текст для Playground. Кнопка `Load free_text` в UI подставляет его в поле plaintext.

### `meta.notes`

Краткие заметки для конкретного набора данных. Сейчас это в первую очередь редакторское поле Data Manager.

### `meta.raw_key_example`

JSON-объект с примером сырого ключа. Playground использует его вместе с `free_text`: при загрузке свободного текста UI пытается подставить и пример ключа.

## Структура `items[]`

`items` — список вариантов. Каждый элемент — объект со следующими полями:

- `id: int` — уникальный идентификатор варианта внутри файла;
- `mode: "encrypt" | "decrypt"` — как интерпретировать `text`;
- `text: str` — исходный текст для запуска варианта;
- `key: dict` — сырой ключ в формате, совместимом с `parse_key()`;
- `expected: str` — необязательное ожидаемое значение результата.

## Инварианты `id/mode/text/key`

Их задаёт `service.validate_variants_obj()` и тесты схемы:

- корень должен быть JSON-объектом;
- `items` обязателен;
- `items` должен быть списком;
- каждый элемент `items[i]` должен быть объектом;
- `id` должен быть `int` и уникален в рамках файла;
- `mode` допускает только `encrypt` и `decrypt`;
- `text` должен быть строкой;
- `key` должен быть словарём;
- `expected`, если присутствует, должен быть строкой.

## Связь с `validate_variants_obj()`

`validate_variants_obj()` — главный инфраструктурный инвариант формата. Его используют:

- `tests/test_service.py` — для unit-проверок валидатора;
- `tests/test_variants_schema.py` — для проверки реальных файлов;
- Data Manager — перед сохранением `meta` и списка вариантов;
- тесты новых наборов данных, например для `ramsey`.

Если документация и код расходятся, приоритет у фактического поведения валидатора.

## Legacy-история: `free_text.txt`

Исторически свободный текст жил в отдельном файле `data/<cipher_id>/free_text.txt`. Текущая модель хранения — внутри `variants.json`, в `meta.free_text`.

Переходный механизм:

- `service.maybe_migrate_legacy_free_text()` проверяет наличие старого `free_text.txt`;
- если `meta.free_text` пуст или отсутствует, содержимое переносится в `variants.json`;
- если в `meta.free_text` уже есть строка, legacy-файл ничего не перезаписывает.

Это значит, что проект ещё умеет мигрировать старые данные, но целевой формат уже один: `variants.json`.

## Как Data Manager использует `meta` и `items`

Data Manager:

- загружает полный корень `variants.json`;
- даёт редактировать `meta.free_text`, `meta.notes`, `meta.raw_key_example`;
- даёт добавлять, заменять и удалять варианты в `items`;
- валидирует весь объект перед сохранением.

Для ключа варианта доступны два режима:

- Form — UI строится по `describe().params`;
- Raw JSON — пользователь правит сырой JSON-объект, который затем отдельно проверяется через `parse_key()`.

## Как Playground использует `meta` и `items`

Playground читает данные только в режиме просмотра:

- вариант из `items[]` подставляется в поля ввода и не меняет файл;
- `meta.free_text` загружается в plaintext;
- `meta.raw_key_example`, если он задан, одновременно подставляется в форму/JSON ключа.

Это важный инвариант: загрузка данных в Playground не должна модифицировать `variants.json`.
